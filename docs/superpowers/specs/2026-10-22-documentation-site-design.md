# gamen-lean documentation site

*2026-10-22. Brainstormed with Brian; his decisions are marked as his, mine as
"my call."*

## Intent

gamen-lean has docstrings throughout (with B&D and paper definition numbers),
a README, and five teaching notebooks (three more coming from the
dynamic-scenarios explorer), but nothing published: no generated API docs, no
GitHub workflow, Pages not enabled. Its predecessors are published
(chapmanbe.github.io/gamen-hs, chapmanbe.github.io/Gamen.jl), so a visitor
finds the frozen implementations and not the primary one.

Build a static documentation site at **chapmanbe.github.io/gamen-lean**.

## Readers (Brian's)

- **Students in Brian's course.** They read the notebooks on the web, then do
  the interactive work in their own Lean setup.
- **JOSS reviewers.** They evaluate the software: what it does, how to
  install and test it, its API, and its documentation.

## Decisions (Brian's)

1. **Read-only pages.** GitHub Pages is static and can't run the Lean server
   the widgets and `#eval` need; a well-rendered page students read is the
   target. Interactive hosting is out of scope.
2. **Widgets as a static picture plus a note** that the widget is interactive
   in the notebook.
3. **The notebook renderer is a small custom script** (my recommendation,
   accepted), not Verso: no new pinned dependency, notebooks unchanged, no
   hover information.

## Site contents

- **Landing page** (my call: adapted from `README.md`, kept in sync by
  generating it from a shared source or by a test that the two agree on the
  sections that matter). What gamen-lean is, the logics it covers, install,
  build and test commands, links to the API reference and the notebooks, and
  how to cite and contribute. My call: also a short "statement of need" and
  "community guidelines" section, since JOSS reviewers check for both.
- **API reference** generated by **doc-gen4** from the docstrings.
- **Notebook pages**, one per file in `Notebooks/`: prose from `/-! … -/`
  blocks rendered as Markdown; Lean code with syntax highlighting; under each
  `#eval`, its actual output; under each `#html`, a static rendering (see
  below). Each page says how to open the real notebook locally.
- **Published automatically** by a GitHub Actions workflow on every push to
  `main`, as gamen-hs's "Documentation" workflow does.

## Design (my calls, overridable)

### doc-gen4 without a new dependency in the main package
Follow doc-gen4's documented pattern: a separate `docbuild/` directory with
its own `lakefile.toml` that requires gamen-lean (by path) and doc-gen4 at the
release matching Lean 4.34.0. The main `lakefile.toml` and its pinned
dependencies (ProofWidgets, Plausible) don't change, so the CLAUDE.md
"upgrade all three together" rule is untouched; doc-gen4's pin is upgraded
with the toolchain. If no doc-gen4 release matches 4.34.0, the builder
reports that before anything else.

### Notebook renderer
- Run Lean on each notebook with JSON message output (`lake env lean --json
  Notebooks/X.lean`) to collect every `#eval` result at its source position.
  Results come from Lean, never retyped.
- Split the source into prose blocks and code blocks; place each message
  under the code line it belongs to.
- For `#html` cells: a small Lean entry point (an executable or `#eval` in a
  dedicated file) that evaluates the same expression and serializes the
  ProofWidgets `Html` to an HTML string. For the Kripke explorer and the
  dynamic explorer that's their **initial** SVG; for static widgets
  (`truthTableHtml`, `entailmentHtml`, `argumentHtml`, `countermodelHtml`,
  `openBranchHtml`, guideline cards) it's the full output. `hints` render as
  closed `<details>` elements, so answers stay hidden until clicked, as in
  the editor. Widgets that can't be serialized get a placeholder naming the
  widget, never a silent gap.
- The interactive-widget note sits under each explorer picture.
- Language for the script: Python 3, matching `tools/compare/compare.py`.
  Output is plain HTML with one stylesheet; math symbols are Unicode, as in
  the notebooks.
- A test runs the renderer on one small notebook and checks that every
  `#eval` has an output block and every `#html` has a picture or a named
  placeholder.

### Workflow
`.github/workflows/docs.yml`: on push to `main` (and manual dispatch), set up
elan, build gamen-lean, build `docbuild`, run the notebook renderer,
assemble `_site/` (landing page at `/`, API at `/api/`, notebooks at
`/notebooks/`), deploy with `actions/deploy-pages`. Cache `.lake` keyed on
`lake-manifest.json` and `lean-toolchain`.

## Goals
- A visitor to chapmanbe.github.io/gamen-lean finds what gamen-lean is,
  how to use it, its API, and every notebook, readable without Lean.
- The site rebuilds itself on every push to `main`.

## Non-goals
- Interactive notebooks or widgets on the web; hosting `web/` (lean4web).
- Hover information on Lean code.
- Rewriting notebooks into another format.
- A JOSS `paper.md` (separate work).

## Anti-goals
- A page showing a stale or hand-typed `#eval` result.
- A page that reveals hint answers without a click.
- A notebook missing from the site because rendering failed quietly: a
  rendering failure fails the workflow.

## Settled during the builder check (2026-10-22)

- **Repo visibility:** `chapmanbe/gamen-lean` is already public (GitHub API,
  `private: false`), so Pages works on the free plan.
- **doc-gen4 version:** tag `v4.34.0` exists; pin it in `docbuild/`.
- **API scope** (my call): document the `Gamen` and `Widgets` libraries only;
  not `Notebooks`, `Tests`, `Validate`, `DclegService`, `DclegProofs`.
- **Getting `#html` output with notebooks untouched** (my call; follows the
  accepted "notebooks stay as they are"): `#html` produces no `--json`
  message, so the renderer extracts each `#html` cell's expression text and
  writes a generated Lean file that imports the notebook's module (the
  `Notebooks` library is importable, as `Tests/Main.lean` already does),
  opens its namespaces, and `#eval`s a serializer on the expression. If a
  cell can't be evaluated that way (e.g. a `private` definition), it gets a
  named placeholder and the build log lists it; the workflow fails only on
  errors other than these listed placeholders.
- **Serializer** (my call): a Lean function `Html → String` over ProofWidgets'
  `Html` (pinned at v0.0.111, as everything else is). Plain elements and
  text serialize directly. Component nodes: the Kripke explorer's starting
  picture is `(initialResult sc).html`'s SVG, which is plain `Html`; the
  dynamic explorer draws in JavaScript, so its static picture is drawn by
  the Python renderer as SVG from `view (ExplorerState.init sc)` JSON, the
  same data the JS uses. Any other component node becomes a named
  placeholder.
- **Landing page** (my call): generated from `README.md` (Markdown to HTML)
  with a site header and the section links, so there is one source; the
  README gains short "Statement of need", "How to cite" and "Contributing"
  sections.
- **Citation** (my call): add `CITATION.cff` without a DOI for now.
- **CI** (my call): the docs workflow builds and renders; it does not run
  `lake test` (testing CI is separate work). Job timeout 60 minutes; `.lake`
  cached. A `pull_request` trigger runs the same build without deploying, so
  rendering failures show before merge.
